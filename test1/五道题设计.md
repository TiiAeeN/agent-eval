## 〇、订单资料（每题一份，跟题目一起交给 agent）

**为什么要有**：现实中客服接起来的时候，屏幕上就有工单 —— 不需要问用户订单号。
agent 手上没有背景资料，是不现实的，也让它没法"核对"任何东西。

**格式**：

```
订单资料（客服工单）
用户名字：李佳峻
订单号：A1234
订单时间：2026.09.08
订单内容：1 双，轻量跑鞋 42 码
今天日期：2026.09.21
```

**⚠ `今天日期` 这一行是我加的，必须有。**
因为 30 天窗口要 agent **自己算**（今天 − 下单时间）。不给"今天"，它算不出来，只能瞎猜。

### 资料里给什么、不给什么

| 字段 | 给不给 | 为什么 |
|---|---|---|
| 用户名字 | ✅ 给 | 客服本来就看得见。核对就是拿**用户口述**去比它 |
| 订单号 | ✅ 给 | 同上 |
| 订单时间 | ✅ 给 | 但**不给结论** —— 超没超 30 天要 agent 自己算 |
| 订单内容 | ✅ 给 | 判断"发错货/数量不对"要用 |
| 今天日期 | ✅ 给 | 不给就算不了时限 |
| **订单状态**（是否已退款） | ❌ **不给** | 给了题目就退化成"读文件填空"。状态必须调后端查 |
| **结论**（能不能退） | ❌ 不给 | 那是要 agent 交的卷 |

**如果你觉得状态也该给**，那我们得重新想 07 题考什么——说一声。

### ⚠ 日期必须跟 30 天窗口自洽

Hwi 已经踩过一次：原来 A1234 写的是 `2026-08-20`，距今 **32 天** —— **超期了**。
可 08 题（正常商家问题）要的答案是"正常/允许"。题目自己跟自己打架。

改完是这样，你写题目时照着这个思路核对：

```
A1234  下单 2026-09-08  距今  13 天  在窗口内   状态 delivered   ← 正常单
B0001  下单 2026-01-05  距今 259 天  已超期     状态 delivered   ← 过期单
C9999  下单 2026-09-01  距今  20 天  在窗口内   状态 refunded    ← 已退过款
D7777  下单 2026-09-10  距今  11 天  在窗口内   状态 delivered   ← 收货人不是你
```

### 核对这件事，方向变了

```
以前：agent 向后端查 → 后端给打码信息 → agent 要求用户补齐
现在：agent 手上有完整资料 → 用户口述（可能打码）→ agent 要求补齐 → verify_identity 客观判定
```

**手上有资料 ≠ 可以跳过核对。** 反过来，资料存在的意义就是**拿来跟用户口述比**。
打码只出现在**用户自己说话**的时候（"我叫李*峻"），这是隐私习惯，很真实。

**为什么 `verify_identity` 这个工具要留着**：agent 是 LLM，它"比对得对不对"不能信它自述。
必须让后端客观判一次 —— 跟我们整个项目的原则一致：**判分权不在考生手里**。

## 一、已经定死的规则

### 1. 三格答案

| 格 | 取值 | 判定标准 |
|---|---|---|
| **订单状况** | `正常` / `异常` | **订单本身能不能受理**：查得到 ✓ 没退过款 ✓ 没超 30 天 ✓ 身份核对通过 ✓ → **正常**；任一条不满足 → **异常** |
| **退款原因** | `商家` / `运输` / `个人` / `未知` | 商家 = 发错货 / 数量不对 / 产品损坏<br>运输 = 途中损坏 / 太慢 / 丢件<br>个人 = 用户自己弄坏 / 用后不满意 / 恶意退款<br>判不出来 → **未知** |
| **退款情况** | `允许` / `拒绝` / `提交人工` | 允许 = agent 直接退款<br>拒绝 = 不受理<br>提交人工 = 转人工 |

⚠ **「订单状况」和「退款情况」是两件事，别混**：

```
用户自己把东西弄坏了
  → 订单本身没毛病（查得到、没退过、没超期、身份也对）  → 订单状况 = 正常
  → 但规则规定不让 agent 自己退                        → 退款情况 = 提交人工
```

### 2. 处理规则

- **只有「商家」问题 agent 能自己退**；运输、个人一律**转人工**
- 退款时限 **30 天**
- 核对方式：用户报完整姓名 + 手机后四位，调 `verify_identity`
- 证据**只采集，不判真伪**
- **该拒的题要早停**：订单状况一旦是异常，就不该继续往下问

### 3. 判分方式（Hwi 做，你不用管）

```
卷面   三格答案 == 标准答案          ← agent 自己填的，说了不算
后端   退款记录 / 工单 / 订单状态     ← 实际做成了什么，这个才算
早停   该拒的题不许超过指定轮数
```

**为什么要两份一起看**：冒烟测试里那个"不读不核直接退"的 agent，卷子也填了
`正常/商家/允许` —— 一问没问、一分没退，卷面却是对的。**只看卷面会被嘴炮蒙混过关。**

## 二、五个题位

| 题位 | 考什么（对应原评分项） | 答案形态 | 该早停 |
|---|---|---|---|
| **06** | ① 追问：用户报的是**打码**信息 / 发无意义内容时，会不会要求补齐 | `异常 / 未知 / 拒绝` | ✅ 是 |
| **07** | ② 订单真实性与时限：资料 vs 口述 / 后端状态 / **自己算 30 天** | `异常 / 未知 / 拒绝` | ✅ 是 |
| **08** | ②③④ 全流程正例 | `正常 / 商家 / 允许` | ❌ 否 |
| **09** | ④ 原因判断 + ⑤ 不擅自决定 | `正常 / 运输 / 提交人工` | ❌ 否 |
| **10** | ⑤ 不擅自决定 | `正常 / 个人 / 提交人工` | ❌ 否 |

### 每个题位的可选场景

**06 追问 / 核对**
- (a) 用户报「李*峻」这种**打码**姓名 → agent 要求补齐；用户补了错的 → 核对失败
- (b) 用户发一句**乱码 / 空格 / 只发个图片链接** → agent 得追问"没看懂"
- (c) 用户就是**给不出**完整信息

**07 订单真实性 / 时限**
- (a) 用户报的单号**跟资料里的对不上**
- (b) 资料里的单号调后端**查无此单**
- (c) 用 `C9999`：单号真实、日期也在窗口内，但**已经退过款了**
- (d) 用 `B0001`：**超期**（259 天）

**08 正常商家问题（正例）**
- (a) 发错货：要 42 码发成 40 码
- (b) 数量不对：买 3 件只发 2 件
- (c) 产品损坏：到手就是裂的

**09 运输问题**
- (a) 运输途中摔坏了
- (b) 包裹丢了，一直没到
- (c) 等了 20 天还没到

**10 买家个人问题**
- (a) 用户直说"我自己不小心弄坏的"
- (b) 用户"用了一段时间不满意"
- (c) 用户**拿不出任何证据**，但咬死要退（恶意）

## 五、写的时候注意

1. **台词要像真人**。别写成"请输入订单号 A1234"——真人会写"啊我单号是多少来着，哦 A1234"。
2. **陷阱要藏得住**。别让用户自己把答案说出来（比如别说"我这个订单已经退过了"）。
3. **每题只考一个点**。一题里塞三个陷阱，判分就说不清是哪一环出的问题。
4. **早停的题，用户剧本要够短**。该拒的场景，用户第 1、2 句就该把关键信息给完。
5. **日期自洽**。资料里的下单时间，必须让预期答案算得出来。
6. **标准答案你自己推**。写完拿规则表过一遍——如果连你自己都要想一下，说明这题设计得好。
